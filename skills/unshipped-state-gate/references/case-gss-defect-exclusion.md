# 사례 — 결함 제외 기능의 미배포 상태 잔재 (gss, 2026-08)

철강 결함판정 시스템의 "결함 제외" 기능. 처음엔 결함 코드 단위로 설계·병합됐고(PR #10),
이후 class id 단위로 전환하는 PR에서 옛 설계의 잔재가 사슬로 쌓였다. 코드 단위 시절은
main에 병합됐지만 **어느 운영 환경에도 배포되지 않았다**.

## 쌓인 잔재 사슬 (전부 같은 미실존 상태를 방어)

방어 대상 상태 = "코드 단위 제외로 저장된 운영 행(defect_class_id가 NULL인 행)".

- 마이그레이션 3단 진화: create(코드 단위 unique, cascade FK) 후 defect_class_id 추가
  후 FK 제거 — 최종 스키마 하나면 될 것을 설계 변천 그대로 재생
- `expandLegacyCodeExclusions()`: 옛 코드 단위 행을 class 행으로 전개하는 변환 함수
  (+ 실패 경고 로그 + 자기 테스트)
- `whereNotNull('defect_class_id')` 가드: NULL 행이 결함과 매칭되는 것을 방어
- `?string $code = null` 파라미터와 "null이면 기존 값 유지" 조건 upsert
- down()의 code-unique 복원 로직과 고아 행 정리
- 프론트의 "구 응답" 폴백: 새 응답 필드가 없으면 옛 방식으로 합산 — 도달 불가일 뿐
  아니라 실행되면 틀린 값(중대 결함 누락)을 내는 위험한 폴백

## 실패한 판정 두 가지

1. **에이전트의 자체 리뷰**: 잔재를 "호환성 배려"로 읽고 통과시켰다. 방어 대상 상태를
   명명하는 단계가 없어서, "혹시 모를 legacy"가 근거 없이 살아남았다.
2. **검증 에이전트 10건의 반박**: "create 마이그레이션이 origin/main에 병합돼 있으므로
   배포된 기능"이라며 스쿼시 제안을 전부 기각했다. git 병합을 배포의 증거로 쓴 오판 —
   실제 배포 여부는 저장소 안에 없는 환경 사실이었고, 사람은 한 문장으로 답할 수
   있었다("배포된 적 없어서 그 상태는 고려 안 해도 돼").

## 결과

리뷰어가 같은 잔재들에 "왜 필요한가요?"·"미사용 시 삭제"를 달았고, 사람의 배포 확인
후 사슬 전체(변환 함수·가드·nullable 분기·마이그레이션 2개·관련 테스트·프론트 폴백)를
걷어냈다. 교훈이 이 스킬의 워크플로다: 상태를 명명하고, 배포는 사람에게 묻고,
지울 때는 상태를 아는 코드 전부를 함께 지운다.
