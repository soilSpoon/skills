# 모듈 깊이 (Module Depth) — John Ousterhout, *A Philosophy of Software Design*

"이 추상화, 인터페이스 비용 대비 숨기는 복잡성이 충분한가?"

모듈의 가치 = **기능(숨기는 복잡성) − 인터페이스 비용(배워야 할 표면적)**.
인터페이스가 작고 기능이 큰 모듈이 **깊고(deep)**, 인터페이스가 기능만큼 큰 모듈은
**얕다(shallow)** — 얕은 모듈은 복잡성을 줄이지 못하면서 배울 것만 하나 더 늘린다.
전형: Unix 파일 I/O는 5개 호출(open/read/write/lseek/close) 뒤에 캐싱·스케줄링·
권한·디바이스를 전부 숨긴다 — 깊다. `wrapUser(u) { return new User(u) }`는 얕다.

이 렌즈는 4축 중 **결합도·응집도의 심화**다: "작게 쪼개라"(가독성 #6, SRP)와
**정면으로 긴장**하므로, 분해 지적에는 반드시 이 렌즈를 교차시켜야 한다.

## 1. 깊은 모듈 vs 얕은 모듈

**원칙** — 모듈(클래스·함수·서비스)을 평가할 때 코드 길이가 아니라
**인터페이스 : 구현 비율**을 본다. 좋은 모듈은 단순한 인터페이스 뒤에 많은
복잡성을 숨긴다. 인터페이스에는 시그니처만이 아니라 **호출자가 알아야 하는 모든
것**(호출 순서 제약, 예외 종류, 설정 의무, 부작용)이 포함된다.

**Before** — 표면적 ≈ 구현. 호출자가 배울 것만 늘었다:
```ts
class UserValidator {
  validateName(u: User): boolean { return u.name.length > 0; }
}
// 호출부: if (!new UserValidator().validateName(user)) throw ...
```

**After** — 검증·정규화·에러 조립을 통째로 숨기는 한 개의 깊은 진입점:
```ts
// parse: 원시 입력 → 유효한 User (실패는 무엇이 왜 틀렸는지 담아 throw)
function parseUser(raw: unknown): User { /* 검증+정규화+에러 메시지 조립 전부 여기 */ }
```

**왜**
- 호출자의 인지 부하가 인터페이스 크기에 비례한다 — 깊이는 그 비율을 개선한다
- 복잡성 은닉(information hiding)이 모듈화의 존재 이유다; 얕은 모듈은 간접층 비용만 낸다
- "클래스가 크다"는 그 자체로 결함이 아니다 — 인터페이스가 크거나 새는 것이 결함이다

## 2. small-functions 교리와의 긴장

Clean Code류 "함수는 무조건 작게, 클래스는 무조건 잘게"는 **분해 자체를 선으로**
본다. Ousterhout의 반론: 잘게 쪼개면 각 조각은 단순해 보이지만, 조각 수와
조각-간 인터페이스가 늘어 **시스템 전체 복잡성은 오히려 증가**할 수 있다
(classitis). 판단 기준을 바꾼다:

- 분해가 정당한 경우 — 쪼개진 조각이 **독립적으로 이해**되고(읽으러 왔다 갔다
  하지 않아도 됨), 인터페이스가 구현보다 훨씬 단순할 때.
- 분해가 해로운 경우 — 조각들이 **conjoined**(한쪽을 이해하려면 반드시 다른 쪽을
  같이 읽어야 함)일 때. 이때 분리는 시점 이동만 늘린다 → 합치는 게 낫다
  (tidying #13 "하나의 더미"와 동일 결론).
- 길이는 프록시일 뿐이다. **10줄 얕은 함수 5개 < 50줄 깊은 함수 1개**일 수 있다.

리뷰 지침: "함수가 길다/클래스가 크다"를 지적하려면 먼저 **쪼갠 결과의 인터페이스
비용**을 계산하라. 쪼개서 표면적이 늘기만 하면 그 지적은 기각된다(AXIS-CONFLICT로
표면화).

## 3. 얕음의 red flags

| Red flag | 신호 | 처방 |
|---|---|---|
| **Pass-through method** | 인자 그대로 다음 층에 넘기기만 하는 메서드(래퍼의 래퍼) | 층 하나를 제거하거나, 층마다 *다른* 추상화를 갖게 재분배 |
| **정보 누설 (information leakage)** | 같은 설계 결정(포맷·프로토콜·스키마)을 여러 모듈이 동시에 알고 있음 — 한 곳 바꾸면 전부 바뀜 | 그 결정을 한 모듈 안으로 은닉 (결합도 축의 어댑터 처방과 동일) |
| **시간 분해 (temporal decomposition)** | 실행 순서(읽기→파싱→쓰기)대로 모듈을 나눠, 같은 지식(포맷)이 여러 모듈에 분산 | 순서가 아니라 **지식 단위**로 묶는다 |
| **설정 떠넘기기 (configuration overload)** | 모듈이 결정을 못 내리고 파라미터/설정으로 호출자에게 전가 | 합리적 기본값을 모듈이 정하고, 설정은 정말 호출자만 아는 것에 한정 |
| **범용-특수 혼합** | 범용 메커니즘 안에 특정 호출자 전용 분기가 박혀 있음 | 특수 케이스를 호출자 쪽으로, 범용 코어는 순수하게 |

## 4. 일반화가 깊이를 만든다

**원칙** — "지금 필요한 것보다 *약간* 범용(somewhat general-purpose)"인
인터페이스가 대개 더 깊다. 특수 메서드 여러 개(`deleteSelection()`,
`deleteLine()`, `backspace()`)보다 범용 프리미티브 소수(`delete(range)`)가
표면적이 작고 재사용된다. 단, **구현까지 미리 범용화하는 것(YAGNI 위반)과
구분** — 인터페이스만 열어두고 구현은 오늘 필요한 만큼만.

## 5. 에러를 존재 밖으로

**원칙** — 예외는 인터페이스의 일부이며 표면적을 가장 크게 늘리는 항목이다.
가능하면 API 의미를 재정의해 예외 상황 자체를 없앤다: `substring` 범위 초과 →
"겹치는 부분 반환"으로 정의하면 예외가 사라진다; `delete` 없는 파일 → "없음을
보장"으로 정의하면 성공이다. 없앨 수 없는 예외는 낮은 층에서 **한 곳**에 모아
처리한다(exception aggregation).

**주의** — fail-loud(진단 가능성)와 모순 아니다: 이 원칙은 *정상 의미로 흡수
가능한* 경계 사례를 정의로 없애라는 것이지, 진짜 오류를 삼키라는 게 아니다.
`catch {}`는 여전히 [MUST] 결함이다.
