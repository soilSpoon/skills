# 정리 (Tidying) — Kent Beck, *Tidy First?*

"지저분한 코드를 만나면, 먼저 (아주 조금) 정리한다 — 단, 행동 변경과 절대 섞지 않는다."

4축이 **무엇이 좋은 코드인가**를 답한다면, 이 파일은 **언제·어떤 단위로 거기에
도달하는가**를 답한다. Tidying = 행동을 보존하는 작은 구조 변경(수 분 단위,
리팩토링의 최소 원자). 핵심은 카탈로그 자체보다 **경제학과 커밋 규율**이다.

## 1. Tidying 카탈로그

각 항목은 **행동 보존**이 자명할 만큼 작다 — 리뷰어가 diff만 보고 "행동 동일"을
30초 안에 확인할 수 있어야 tidying이다. 못 하면 그건 리팩토링(별도 작업)이다.

| # | Tidying | 신호 → 행동 |
|---|---|---|
| 1 | **가드 절 (guard clause)** | 중첩 조건 안에 본 로직 → 전제조건을 early-return으로 빼고 본문을 평평하게. 단, 가드 7~8개면 오히려 악화 — 그땐 함수 분리 |
| 2 | **죽은 코드 삭제** | 실행되지 않는 코드 → 그냥 지운다. "나중에 쓸지도"는 git history가 담당 |
| 3 | **대칭 정규화 (normalize symmetries)** | 같은 일을 하는 코드가 곳마다 다른 모양(lazy-init 5가지 스타일 등) → 한 가지 모양으로 통일 |
| 4 | **새 인터페이스, 옛 구현** | 쓰기 불편한 인터페이스 → 원하는 인터페이스를 새로 만들어 옛것을 호출만 하게. 호출부는 점진 이주 |
| 5 | **읽기 순서 (reading order)** | 파일 안 요소가 이해 순서와 다르게 배치 → 독자가 만나야 할 순서로 재배열 (선언 순서에 의미가 없는 언어에서) |
| 6 | **응집 순서 (cohesion order)** | 같이 바뀌는 코드가 멀리 떨어짐 → 나란히 놓는다 (같은 파일 인접 → 같은 디렉토리 → 최소한 같은 리포) |
| 7 | **선언·초기화 이동** | 변수 선언과 첫 사용이 멀다 → 사용 직전으로 이동 |
| 8 | **설명 변수 (explaining variable)** | 큰 표현식 → 부분식을 의도가 드러나는 이름의 변수로 추출 |
| 9 | **설명 상수 (explaining constant)** | 매직 넘버/리터럴 → 의미를 담은 상수로 |
| 10 | **명시적 파라미터** | 함수가 map/env/전역에서 암묵적으로 값을 꺼냄 → 시그니처에 드러나는 파라미터로 |
| 11 | **문장 덩어리 나누기 (chunk statements)** | 한 함수 안 논리 단락들 → 빈 줄로 구획 (추출 전 단계로도 유효) |
| 12 | **헬퍼 추출 (extract helper)** | 목적이 뚜렷하고 상호작용이 좁은 블록 → 이름 있는 함수로 추출. **바뀔 부분을 먼저 추출해두면 행동 변경 diff가 최소화됨** |
| 13 | **하나의 더미 (one pile)** | 잘게 쪼개져 오히려 전체 파악이 안 되는 코드 → 일단 한곳에 합쳐 읽고, 다시 좋은 경계로 나눈다 (분해가 항상 선은 아니다) |
| 14 | **설명 주석** | 코드에서 자명하지 않은 "왜"(불변식, 함정, 외부 제약) → 그 자리에 기록. **무엇** 주석은 쓰지 않는다 |
| 15 | **중복 설명 주석 삭제** | 코드가 이미 말하는 것을 되풀이하는 주석 → 삭제 (코드를 주석 수준으로 명확하게 만든 뒤) |

리뷰에서 이 카탈로그는 **처방의 언어**다 — "복잡하다"라고 지적하는 대신
"가드 절 + 설명 변수 2개면 평평해진다"처럼 tidying 이름으로 처방한다.

## 2. 두 모자 — 커밋 분리 규율

**한 커밋(최소한 한 PR)에는 한 종류의 변경만**: 구조 변경(tidying, 행동 동일)
또는 행동 변경(기능/버그픽스). 절대 섞지 않는다.

- 섞인 diff는 리뷰어가 "어느 줄이 행동을 바꾸나"를 전 줄에서 판별해야 한다 —
  리뷰 비용이 곱으로 뛰고, 회귀 원인 추적(bisect)도 오염된다.
- 구조 커밋은 "행동 동일" 하나만 검증하면 되므로 리뷰가 빠르고, 롤백도 안전하다.
- 작업 중 tidying 욕구가 생기면: 지금 diff가 작으면 **먼저 tidy 커밋 → 행동 커밋**,
  이미 행동 변경이 진행 중이면 메모해 두고 **행동 커밋 후 tidy 커밋**. 중간에 섞지 않는다.

이것은 slice의 두 모자(behavior then structure) 규율의 커밋-수준 표현이다.

## 3. 언제 정리하는가 — 경제학

Tidying은 도덕이 아니라 **투자 판단**이다. "지저분한 코드 = 항상 정리"가 아니다:

| 시점 | 판단 |
|---|---|
| **Tidy first? (변경 전)** | 정리하면 이번 행동 변경이 쉬워질 때만. 기준: *"지금 어렵게 하는 일 → 정리 → 쉬워진 일"* 이 총합으로 더 싸다 |
| **Tidy after (변경 후)** | 같은 영역을 곧 다시 만질 게 확실하고, 지금 정리 비용이 미래 절감보다 쌀 때 |
| **Tidy later (백로그)** | 위 둘 다 아니면 기록만 하고 지나간다 |
| **Tidy never** | 다시 만질 일 없는 코드는 지저분해도 그대로 둔다 — 정리 비용을 회수할 수 없다 |

돈의 시간 가치: **지금 버는 돈 > 나중 버는 돈, 나중 쓰는 돈 > 지금 쓰는 돈.**
행동 변경(가치 창출)을 지연시키는 대규모 선정리는 그래서 대개 손해고, tidying이
수 분 단위로 작아야 하는 이유도 이것이다. 반대 항: 정리는 **옵션(option)을 산다** —
구조가 유연하면 미래 변경 가능성이 전부 싸진다. 확실히 다시 만질 코드일수록 옵션
가치가 커서 정리가 정당화된다.

## 4. 묶음 크기

tidying 여러 개를 모아 한 번에 내면(대형 "cleanup PR") 리뷰 지연·충돌·회귀
리스크가 묶음 크기에 비례해 커진다. **tidy 커밋은 작게, 자주, 즉시 머지**가
기본값이다. "cleanup 브랜치를 오래 끌고 간다"는 신호 자체가 안티패턴.
