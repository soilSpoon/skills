# issue-driven — 이슈가 spec, 실행은 규율

역할 분담이 고정이다: **사람 = 판단** (무엇을 만들지, 어떤 테스트가 통과해야 하는지,
결과 검증) / **에이전트 = 실행** (red→green→tidy→gate, 정직한 보고). 코드 생산이
싸진 세계에서 병목은 판단이다 — 좋은 이슈를 쓰는 것이 곧 개발이고, 에이전트의
가치는 이슈를 흔들림 없이 완주하는 신뢰성이다.

## 이슈 = 위임 단위의 규격

[templates/agent-task.md](templates/agent-task.md)가 원본. 필드는 slice lane spec에서
실전 검증된 것들이다 (각 필드는 실제 결함 클래스 하나씩과 대응):

| 필드 | 왜 있는가 |
|---|---|
| **Purpose** | 끝났을 때 사용자가 관찰하는 변화 — "코드가 어떻게"가 아니라 "무엇이 달라지는가" |
| **Test cases** | 오너가 설계한 수용 기준. 각 항목이 에이전트의 첫 red 테스트가 된다 — 케이스가 곧 명세 |
| **Evidence / Context** | 관련 `file:line`·재현 절차·과거 결정. 진단은 위임 **전에** 끝낸다 |
| **MUST PRESERVE** | 테스트 없는 기존 행동 중 회귀 금지 목록 |
| **Wiring** | 기능이 노출되는 실제 프로덕션 경로 — built-but-unwired가 재발 1위 결함 클래스 |
| **Rules** | 기본 = repo AGENTS.md + code-fundamentals. 이 작업에서 조정할 렌즈만 명시 |
| **Discovery policy** | 기본 = 발견 항목은 BACKLOG **기록만**. sweep은 명시적 opt-in + cap (실측: 무단 체이닝은 4리프 50분을 11리프 100분+로 만든다) |
| **ETA** | 시간도 수용 기준이다 — 납기는 신뢰성의 1급 축 |

설치: 대상 리포에 `.github/ISSUE_TEMPLATE/agent-task.md`로 복사 (GitHub 리포).
GitHub이 아니면 `docs/issues/NNN-slug.md` 파일로 같은 규격을 쓴다 — 규격이 본질이지
호스팅이 아니다.

## 실행 규율 (에이전트 측 — 모든 이슈에 동일)

1. **이슈 전문을 읽고, 시작 전 ETA를 코멘트한다.** 초과 조짐이 보이면 조기 보고 —
   조용한 지연은 조용한 실패다. spec 공백이 실행을 막으면 추측하지 말고 물어서 이슈에
   기록을 남긴다 (논의가 이슈에 쌓이는 것이 이 모델의 핵심).
2. **게이트를 발견한다, 가정하지 않는다.** 빌드/테스트 방법은 리포마다 다르다 —
   AGENTS.md/CLAUDE.md → 스크립트(`scripts/`, `Makefile`, `package.json`) → 관례 순으로
   찾고, 없으면 확인해서 이슈에 기록한다. 프로젝트 지식은 리포에 남기지, 스킬로
   일반화하지 않는다.
3. **오너의 테스트 케이스에서 red부터.** 케이스 하나 → 실패 확인 → 구현 → 필터드
   green, 한 번에 하나씩. 이너 루프는 필터드 테스트, 전체 스위트는 마지막에 한 번.
4. **두 모자.** 행동 변경과 구조 정리(tidy)는 커밋을 섞지 않는다. 정리가 필요하면
   tidy 커밋을 앞뒤로 분리한다.
5. **커밋은 이슈를 참조**하고, 신뢰 단위 하나당 하나. 합이 sprawl하면 squash해서 landing.
6. **네 불변식은 여기서도 산다**: 실행자≠검증자(오너 검증 or 리뷰 렌즈), 모델 판단보다
   shell truth, 신뢰 단위=커밋, full suite는 통합 시점.

## 보고 (Verification 단계로의 handoff)

완료 시 이슈에 **trust ledger 코멘트**를 남긴다:

- 케이스별 pass/fail (테스트 이름·명령 포함 — 오너가 재실행 가능하게)
- MUST PRESERVE 검증 방법과 결과
- 벗어난 것·미해결·스킵을 **먼저** (묻어두기 금지 — 검증되지 않은 것을 검증됐다고
  말하는 순간 이 모델 전체가 무너진다)
- 발견 항목 → BACKLOG 기록 (링크)
- 오너 hand-verify 절차: 무엇을 열고 무엇을 눌러 무엇이 보여야 하는지. UI 작업이면
  실행해서 픽셀을 직접 확인한 뒤 넘긴다 — green ledger는 테스트 통과의 증명이지
  사용자가 기능을 볼 수 있다는 증명이 아니다.

오너가 verify 후 close — close는 오너의 것이다.

## 팬아웃이 필요할 때 (예외)

이슈 자체가 병렬 모양일 때만: 리뷰/감사 → slice `templates/review.js`, 커스텀 다중
에이전트 → slice `templates/primitives.md` 조립. **빌드형 이슈의 기본은 인라인 실행이다**
— 실측으로 인라인 15~20분 vs 오케스트레이션 lane 110분. 병렬 기계는 병렬성이 실제로
벌어줄 때만 값을 한다.

## 오너의 규칙 조정 레버

- **품질 렌즈**: skills(code-fundamentals + tidying/depth 등) 편집 — 리뷰·실행에 자동 반영
- **리포 로컬 규칙**: 각 리포 AGENTS.md — 게이트·관례·when-choices
- **작업별 조정**: 이슈의 Rules/Discovery/ETA 필드
